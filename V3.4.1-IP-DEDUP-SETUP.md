# V3.4.1 — Duplicate IP protection
Ships OFF; cannot affect existing traffic until activated deliberately.

## Function
- One successful invitation redirect per Cloudflare edge public IP in the configured rolling window (default 24h).
- The next same-network request gets HTTP 429 and no WhatsApp Location header.
- The Worker stores keyed HMAC-SHA256 digests, not raw IPs; digest and expiry in D1; atomic SQLite UPSERT for collisions.
- Compatible with legacy /join and future protected /join.
- This does not confirm WhatsApp membership; access to the original WhatsApp URL can be shared out-of-band.

## Limits
Carrier-grade NAT and public Wi-Fi can put multiple legitimate people on one IP. A VPN or new cellular IP can evade the guard. IP is not a unique person.

## Enable after acceptance
1. Cloudflare D1 Production angel-research-links-v33 > Console: execute migration conversion-worker/migrations/0002_v341_ip_dedup.sql.
2. Cloudflare Worker > Settings > Runtime variables and secrets: create a new independent 64-hex-character Secret called LINK_IP_HASH_KEY (never send it or put it in GitHub).
3. Check /health; it must report ipDedupEnabled:false initially.
4. Configure LINK_IP_DEDUP_ENABLED=true and LINK_IP_DEDUP_HOURS=24 as ordinary runtime variables. Keep LINK_MODE_ENABLED=false for now.
5. Verify a first test request redirects, a repeat same-IP request returns 429, another network is allowed, and no WhatsApp original invite appears in the 429.
6. Monitor legitimate-carrier-IP false positives. Immediately change LINK_IP_DEDUP_ENABLED=false to disable.
7. Run scheduled expired-key cleanup and disclose 24h keyed network-IP anti-abuse purpose and retention in the privacy statement.

Cloudflare dashboard runtime variables may be overwritten by later Wrangler/GitHub deployment. Keep Wrangler's config synchronized after activation.
