# Angel Research · V3.2 private conversion dashboard

## Current status (2026-10-14)

**Deployed code:** `analytics-dashboard.html` + responsive CSS/JS, `/report` Worker route, direct Cloudflare Analytics SQL binding, CSV exports, local-only cost/impression/verified-join fields. The existing V3.1 `/collect`, `/join`, `/health` endpoints and GA4 are unchanged.

**Activation remaining:** The Cloudflare Worker needs one **owner-controlled private secret**, named exactly `REPORT_ACCESS_KEY`. Until it is present, the private `/report` API returns HTTP **503** without releasing any analytics. Do not paste the secret in ChatGPT, GitHub, email, screenshots, or any public page.

Cloudflare Analytics SQL Workers binding is available with Wrangler >=4.145 (uses the account-scoped `[analytics] binding = "ANALYTICS_SQL"` already in the Worker config), so **you do NOT need any Account Analytics API token**.

## How to set up the private dashboard

1. Open the site owner console in one browser tab:
   https://angelresearchindia.com/analytics-dashboard.html
2. Click **Generate & copy secure owner key**. The page generates a 64-character random hexadecimal key with your own browser's secure cryptographic random API. It fills the password field and copies the key to your clipboard. The key is **not sent to GitHub or stored by the website**.
3. In a **second tab**, open [Cloudflare Workers](https://dash.cloudflare.com/) → **Compute → Workers & Pages → angel-research-conversion-v31 → Settings**.
4. Find **Variables and Secrets** (naming may vary) → **Add**. Enter exactly:
   - Name: `REPORT_ACCESS_KEY`
   - Type: **Secret / Encrypt**
   - Value: paste the randomly generated key from your clipboard. Do not put the key into a public plain-text variable or Wrangler TOML.
   - Save / Deploy. Cloudflare may create a new Worker version.
5. Return to the original private dashboard tab (the password field still holds the generated key). Click **Unlock live reports**.
6. Check the **7 days** filter, `page_view` / `join_click` totals, daily chart and campaign table.
7. If your Worker has not yet written Analytics Engine event data, results may be empty; run a source-specific test:
   https://angelresearchindia.com/ipo-community.html?utm_source=x&utm_medium=influencer&utm_campaign=test_v32
   Then tap the join button once. Wait for ingestion and refresh the private report.
8. Confirm the final WhatsApp invitation still opens normally. It is an independent destination: redirects DO NOT mean successful joins.

## What the reports show

- **Cloudflare automatic:** aggregated eligible `page_view` and `join_click` events, campaign and source, daily UTC trend, country breakdown and event ratio. The SQL interface weights its `COUNT(*)` on adaptively sampled datasets. Results may be approximate.
- **Owner-entered locally:** campaign fee (INR), X post impressions and actual confirmed WhatsApp joins. Saved only in browser localStorage for this web origin. **Not synced across devices**.
- **Cost calculations:** Only when confirmed actual joins and spend exist. No fake visitor/confirmed join counts and no invented defaults.
- **GA4:** Remains independently connected and consent-gated. This dashboard does not merge GA4 and Worker numbers, which may have different populations.
- **Actual memberships:** Must be counted from WhatsApp admin evidence. Cross-campaign attribution requires approved unique invitation links or evidence; otherwise treat numbers as unverified.

## Security

- The static HTML is public to load, but **all actual report data is protected** by Cloudflare Worker secret `REPORT_ACCESS_KEY`. Minimum 32 characters; generated key is 64 hex chars.
- The key stays only in browser memory while logged in; it is never stored in localStorage, cookies, query strings, GitHub source, analytics events or Cloudflare Analytics Engine event rows.
- Only whitelisted site origins get cross-origin permissions. Source whitelist is not a security substitute for the owner secret.
- Worker `/report` supports only 1, 7, 30-day bounded queries, returns aggregate rows rather than raw activity, and fails closed if unconfigured.
- When you press **Lock**, the key is discarded from memory. It also disappears on refresh or after closing the tab.
- Do not expose access keys in developer tools recordings or screenshots.
- If the key is lost, replace the secret in Cloudflare with a fresh generated key. Do not try to retrieve the old secret.
- Avoid putting the dashboard on an open public screenshot for ad visitors; the data itself remains protected.

## Troubleshooting

- **HTTP 503 reporting_not_configured:** The `REPORT_ACCESS_KEY` secret is absent, too short, or `ANALYTICS_SQL` is not bound to the Worker. Confirm Worker production bindings and redeploy.
- **HTTP 401 unauthorized:** The key entered in the dashboard does not match the secret saved in Cloudflare.
- **HTTP 502 report_query_unavailable:** Confirm Analytics Engine is enabled, dataset `angel_research_conversion_v31` has incoming events, and the new Analytics SQL binding is compatible with the account. Check Cloudflare Worker Logs; they may require enabling observability.
- **Empty campaigns:** Generate one eligible visit + redirect through the V3.1 landing link, then refresh after several minutes; do not confuse health requests with page views.
- **Browser privacy rejection / blocked requests:** Not every visitor will be counted. Privacy preferences must be respected.
- **CSV export:** Uses actual report rows merged with owner-entered manual values, with spreadsheet-formula-safe escaping.
