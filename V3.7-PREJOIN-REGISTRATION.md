# V3.7 pre-WhatsApp lead registration

**Stage only**: `JOIN_LEAD_FORM_ENABLED=false` in Wrangler. Existing V3.6 production dynamic `/join` keeps working until rollout prerequisites and approval.

## New user journey
Website CTA -> Worker GET /join -> branded required Full Name + Indian WhatsApp number (+91 and 10 digit local) -> required specific invitation data-processing checkbox -> optional research updates checkbox (unchecked by default) -> POST to same Worker /join -> D1 writes personal data -> 303 direct dynamic current WhatsApp main group A.

Data uses HTTPS form POST body only. The name and phone never appear in the query string, Analytics Engine, WhatsApp redirect Location, or public HTML. One-time HMAC form token uses the **existing LINK_ADMIN_KEY** (not an additional administrator login password). A replay does not produce additional records. No public IP is stored with contact records.

## Private owner records
V3.7 dashboard adds 客户登记 (customer registrations): newest 50 per page, CSV export of current page after confirmation, DELETE one record. All operations require V3.5 signed owner admin session, not public access. Records are deleted by daily Cron after 90 days. This is consent to process invitation, not proof of actual WhatsApp membership.

## Must complete before enable
1. In Cloudflare production D1 `angel-research-links-v33` Console run `conversion-worker/migrations/0004_v37_community_leads.sql` (both statements). Do not use `-preview`.
2. The owner nominated `support@angelresearchindia.com` for privacy/data deletion enquiries. The site Privacy and Contact pages and V3.7 registration form now show it. **Before enabling, verify the mailbox is configured to receive replies** (send a test email and confirm receipt) and approve the stated purposes and 90-day retention. Merely listing an email address does not establish that delivery works.
3. Test the staging gate with sandbox/form data or an isolated test Worker first. Do not insert made-up production data.
4. Set `JOIN_LEAD_FORM_ENABLED=true` in `conversion-worker/wrangler.toml` in a separate rollout PR, then deploy. Do not flip `LINK_MODE_ENABLED`: X/FB/INS/YT and Indian-IP source filters remain separate, not enabled in V3.7.
5. Visit /join. Confirm consent and form inputs, submit test real info with permission, verify response is 303 to main A, and use owner login > 客户登记 to confirm record.
6. Ensure repeat form token is rejected, generic refresh without re-submission shows a fresh form, and wrong phone is rejected.
7. If any outage, set JOIN_LEAD_FORM_ENABLED=false then deploy; V3.6 direct `/join` resumes without DB dependency.

## Compliance and limits
- Indian DPDPA or other relevant requirements depend on deployment dates and applicability: obtain legal/privacy review for exact notice and grievance/withdrawal procedure before activation.
- This flow deliberately does not send unsolicited messages unless the optional outreach checkbox was selected; consent for invitation is not marketing permission.
- The WhatsApp original invite can still be forwarded by someone who receives it. WhatsApp admin approval is separate.
- A form is not proof of a unique person or a real WhatsApp join. India IP and verified social origin controls have not been enabled.
- Existing `/apply.html` Google Apps Script research-update form remains separate and unchanged; community onboarding does not add age, email or investment information fields.
